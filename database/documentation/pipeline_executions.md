# Database Table: `pipeline_executions` Documentation

---

## 1. Table Overview & Purpose

The `pipeline_executions` table serves as the primary **macro-level execution ledger** for multi-agent workflows in FinanceFlow AI. 

When a multi-agent pipeline is triggered (e.g., *Reconciliation & Risk Evaluation Pipeline*, *End-to-End Compliance Audit*), a master record is created in `pipeline_executions`. It tracks the workflow lifecycle (`queued` $\rightarrow$ `running` $\rightarrow$ `completed`/`failed`), total token consumption aggregated across all constituent agents, end-to-end duration in milliseconds, and the distributed `correlation_id`.

```
                    Incoming Trigger (Webhook / UI / API)
                                     │
                                     ▼
                   [ pipeline_executions: STATUS 'queued' ]
                                     │
                                     ▼
                          Priority Queue Dispatches
                                     │
                                     ▼
                  [ pipeline_executions: STATUS 'running' ]
                                     │
                    ┌────────────────┴────────────────┐
                    ▼                                 ▼
           All Steps Succeeded                Step Fatal Error
                    │                                 │
                    ▼                                 ▼
        [ STATUS 'completed' ]                [ STATUS 'failed' ]
```

---

## 2. Table Schema Definition

```sql
CREATE TABLE IF NOT EXISTS pipeline_executions (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    pipeline_name VARCHAR(100) NOT NULL,
    trigger_source ENUM('event_webhook', 'manual_ui', 'scheduled_cron', 'api_direct') NOT NULL DEFAULT 'manual_ui',
    triggered_by INT UNSIGNED NULL,
    status ENUM('queued', 'running', 'completed', 'failed', 'cancelled') NOT NULL DEFAULT 'queued',
    context_data JSON NULL,
    correlation_id VARCHAR(64) NULL,
    total_tokens INT UNSIGNED NOT NULL DEFAULT 0,
    duration_ms INT UNSIGNED NOT NULL DEFAULT 0,
    error_message TEXT NULL,
    started_at TIMESTAMP NULL,
    completed_at TIMESTAMP NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_pipeline_status (status),
    INDEX idx_pipeline_correlation_id (correlation_id),
    INDEX idx_pipeline_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

---

## 3. Data Flow & Integration Lifecycle

1. **Trigger Phase**: The Orchestrator creates a new row with `status = 'queued'`, storing the trigger parameters (e.g. `{ case_id: 20, company_id: 5 }`) in `context_data`.
2. **Execution Phase**: When the priority worker picks up the job from `agentQueue.service.js`, `status` transitions to `'running'` and `started_at` is stamped.
3. **Step Aggregation Phase**: As child agents in `pipeline_steps` complete, their tokens and durations are accumulated.
4. **Finalization Phase**: When all steps finish (or an unrecoverable failure occurs), the record is finalized with `status = 'completed'` or `'failed'`, `duration_ms = completed_at - started_at`, and total LLM tokens.

## 4. Mentor Interview Questions & Answers

### Q1: What is the architectural difference between `agent_runs` and `pipeline_executions`?
**Answer**: `agent_runs` tracks a **single standalone agent execution** (e.g., Agent 1 running Groq LLM tool-calling for one case). `pipeline_executions` represents a **macro multi-agent choreography/workflow** that may coordinate 2, 3, or 6 distinct agents in a specific dependency chain (e.g., Agent 1 $\rightarrow$ Agent 2 $\rightarrow$ Agent 3).

### Q2: Why is `context_data` stored as a JSON column?
**Answer**: Different pipelines receive different input payloads (e.g., a reconciliation workflow receives `{ case_id: 101 }`, while an executive portfolio snapshot receives `{ date_range: "Q3-2026", min_loan_amount: 50000 }`). A JSON column provides schema flexibility while maintaining relational constraints on statuses and timestamps.

### Q3: How do Correlation IDs connect `pipeline_executions` to logs?
**Answer**: The `correlation_id` column matches the `X-Correlation-ID` header generated by `correlation.middleware.js` and stored in `audit_logs`. This allows DevOps engineers to trace an entire multi-agent pipeline back to the exact HTTP request, user session, and structured console logs.
